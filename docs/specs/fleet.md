# Fleet controller

History: designed in #13 and shipped in #19 (v0.12.0); later changes in #24, #48, #53, #70, #74 and #85 (see `docs/releases/`).

## Purpose

- `rootfiles fleet` runs on an operator machine (Linux or macOS) and drives the existing per-host commands (`status`, `check`, `doctor`, `apply`, `update`, `schedule`) over the system `ssh` client against hosts listed in an operator-owned inventory.
- Hosts keep running rootfiles as a single-host tool. The controller adds no agent or daemon to them; the only host-side piece is the read-only sudoers rule written by the `users` module (`internal/module/fleet_sudo.go`).
- Monitoring exporters and the hub are separate specs: [monitoring-exporters](monitoring-exporters.md), [monitoring-hub](monitoring-hub.md). This spec owns only `fleet targets`, which renders and pushes the hub's scrape targets.

## Contracts and invariants

Decisions (still in force):

| Decision | Owner | Limits | Revisit when |
|---|---|---|---|
| Fleet features live in a controller subcommand on the operator machine that drives the existing per-host commands over SSH | user | No agent or daemon on hosts beyond what modules install | A fleet outgrows SSH fan-out (hundreds of hosts) |
| The controller shells out to the system `ssh` client | AI proposes, user picks | Inherits `~/.ssh/config` (`ProxyJump`, agents, `known_hosts`); host key checking is never disabled | A platform without OpenSSH must be supported |
| The inventory is an operator-owned YAML file kept outside this repository | user | `fleet init` creates an inventory; the schema and validator remain strict | - |
| The controller never asks for, stores or forwards sudo passwords; remote privilege is `sudo -n` or a root login, set per host | user | A host whose sudo needs a password is reported `needs-privilege` | - |
| Mutating fleet commands run one host at a time and stop at the first failure | user | Parallelism only for read-only commands | Rollout time becomes the bottleneck |
| A coordinated fleet shutdown uses one shared absolute UTC instant, with serial scheduling and all-or-nothing rollback | user (#134) | Stays inside the serial-mutation decision above; parallel SSH `poweroff` was the rejected alternative | Staggered order or per-group delays are wanted |

- 2026-10-03: read-only fleet commands get passwordless privilege through a sudoers drop-in that allows only the exact `status`, `check` and `doctor` command lines, managed by the `users` module. Mutating commands keep requiring a root login or full sudo. Basis: owner decision on #13.
- Rejected: Ansible (a second source of truth without `check`/`doctor` semantics), `x/crypto/ssh` (would re-implement `ProxyJump`, agents and `known_hosts`), a pull-based agent (a new privileged daemon per host), a metrics collector in the controller (Prometheus already does it).

Invariants an agent must keep:

- **Fixed remote command lines.** OpenSSH passes the remote command to a shell as one string, so it may contain only fixed tokens and validated values, shell-quoted (shared `fleet.ShellQuote` in `internal/fleet/ssh.go`, also used by CLI scripts and backup). The destination follows `--` (`runWithTimeout`), so an inventory value cannot become an ssh option. Site configs travel on stdin, never as arguments.
- **Sudoers and remote command must match byte for byte.** `fleetSudoCommands` in `internal/module/fleet_sudo.go` lists `/usr/local/bin/rootfiles status|check|doctor -o json`; `SSHRunner.ReadOnly` in `internal/fleet/ssh.go` builds exactly `remoteBinary + " " + op + " -o json"`. Changing either side without the other breaks every `sudo: nopasswd` host. No wildcard and no `--config` is ever allowed in the rule.
- **Inventory is strict.** `LoadInventory` (`internal/fleet/inventory.go`) uses `KnownFields(true)`, accepts one YAML document, defaults `sudo: nopasswd` and `parallel: 2` (range 1-128), and rejects unsafe host names, groups, `ssh` destinations (leading `-`, whitespace, shell metacharacters, malformed `user@`/IPv6) and addresses.
- **Site configs resolve on the controller.** `config` paths resolve relative to the inventory file, after following symlinks (a path that does not exist yet uses the given directory), and load through `config.LoadSite`, which ignores the controller's `ROOTFILES_*` environment, requires `users.home_base` (#24) and runs `Validate()`. A config that resolves an inline `tunnel_token` is refused; use `tunnel_token_file`. The resolved YAML (`Host.EffectiveConfig`) and `cfg.Fingerprint()` are computed once at load.
- **Applied provenance.** Read-only results compare the remote `applied_config_sha256` with the inventory fingerprint (`compareFingerprint`). A mismatch is `drift`; a missing fingerprint is `error` with "inventory configuration is unverified", never success. The original health state is kept in `health_state`. Any change to what `config.Fingerprint` hashes shows up here (#85); see [config](config.md).
- **Ping is read-only.** `fleet ping` checks the fixed remote binary version, verifies root login or runs the exact existing `sudo -n` read-only status command, and reports connectivity, key and privilege failures without altering host-key checking or writing to hosts. A successful sudo probe proves only that the command worked in that SSH session; cached credentials may allow it even when the rule is not NOPASSWD.
- **Controller reports are local.** On non-Linux systems `doctor` checks the SSH client, inventory ownership and permissions, local identities, writable log directory and release version without connecting. `status` shows inventory counts and the latest logged result for each host.
- **Onboarding is local.** `fleet init` writes a 0600 inventory under a 0700 newly created directory; it backs up an existing file before overwrite. Its dry run prints YAML. SSH import reads concrete aliases and Include files without connecting, skips unsafe names and patterns, and validates the result. `fleet hosts` validates and lists the inventory without invoking SSH; without selectors it lists all hosts.
- **Selection is explicit.** `Inventory.Select` returns hosts in inventory order; `--host` and `--group` form a union; `--all` cannot be combined with them; an empty selection is an error for fleet reports and rollouts; `fleet hosts` and `fleet targets` default to all.
- **Mutations need `--yes` and a selection** (`authorizeFleetMutation`), and run through `serial` in `internal/fleet/rollout.go`. After the first host whose state is not `ok`, `apply-pending` or `skipped-unreachable`, the remaining hosts are reported `skipped`.
- **Timeouts are bounded.** Read-only SSH calls use at most 45s; mutations default to 15m and `--timeout` must be positive and at most 24h (`ValidateMutationTimeout`), checked before any SSH call. SSH runs with `BatchMode=yes` and `ConnectTimeout=15`.
- **Versions are pinned.** `update` and `bootstrap` require `--version vX.Y.Z` (`ValidateVersion`).
- **The controller writes only operator-owned files**: the run log (`AppendRunLog`, `$XDG_STATE_HOME/rootfiles/fleet.jsonl` or `~/.local/state/rootfiles/fleet.jsonl`, file 0600, directory 0700). It takes no host lock and is not in `mutatingCommands`; remote native commands keep their own root and lock preflight.

## Behaviour

- Report commands accept `--json` as an alias for `-o/--output json`, alongside `-o/--output text`. `writeFleetResults` uses `ui.WriteTable` for text: HOST and STATE, plus REASON when any host has one. All-empty columns are dropped, so an all-`ok` status report with empty reasons shows only HOST and STATE. REASON wraps to the terminal width (or explicit `COLUMNS` on a pipe), subject to a minimum of 20 cells or its heading width. A narrower terminal may have overflowing lines instead of one-character wrapping. A host may occupy multiple display lines. JSON results use the shared CLI encoder with HTML escaping enabled, retaining the previous bytes and without human wrapping. Native reports keep HTML escaping disabled. Text results return the first output-writer error, as JSON results do. Controller findings use shared exitDrift (still 2); remote command lines are unchanged.
- Controller usage errors exit 2: Cobra flag parsing (including unknown flags and values that cannot be parsed), unknown commands, wrong positional counts (`installOutputBoundary` / `usageError`), unsupported `-o/--output` formats and `--json` conflicts (`outputFormat`). For example, `-o yaml` and `--json -o text` exit 2.
- Parsed flag-value validation and other controller/inventory errors exit 1: `--parallel 0` (`newFleetReadCmd`), `--timeout 0` (`fleetMutationTimeout`), invalid versions (`fleet.ValidateVersion`), an unknown schedule action (`fleet.Schedule`), `--on-calendar` on disable (`newFleetScheduleCmd`), refused native flags (`validateFleetFlags`), missing required `--yes` (`authorizeFleetMutation`) and missing explicit rollout selection or an invalid selection (`loadFleetSelection` / `Inventory.Select`). Completed host reports retain their separately documented exit 0/2 rule below.

- `fleet targets` honors explicit host/group/all selectors; an omitted selector retains whole-inventory rendering. Explicit empty/unmatched selectors never fall back to all hosts.
- `fleet schedule enable --on-calendar EXPR` passes a validated, shell-quoted expression; omitted calendar keeps the prior remote enable/disable command bytes. Disable refuses a calendar. Read-only/native report and apply/update wire flags remain accepted.
- Fleet dry-run skips the real-rollout yes requirement but retains explicit rollout selection; real mutations still require confirmation.

Inventory example (default path `$XDG_CONFIG_HOME/rootfiles/fleet.yaml`, else `~/.config/rootfiles/fleet.yaml`):

```yaml
defaults:
  sudo: nopasswd          # nopasswd | root | none
  parallel: 2
hosts:
  gpu01:
    ssh: gpu01            # ssh destination: config alias or user@host
    address: 203.0.113.11 # scrape address as seen from the monitoring hub
    groups: [gpu]
    config: sites/gpu01.yaml
```

- **Read-only** `fleet status|check|doctor [selection] [--parallel N] [-o text|json] [--json]`: runs `[sudo -n] /usr/local/bin/rootfiles <op> -o json` on up to `--parallel` hosts at once (`runReadPool`). Host states: `ok`, `drift` (check exit 2 with valid JSON stdout, a status listing unsatisfied modules, or a fingerprint mismatch), `findings` (doctor exit 2 with valid JSON stdout), `needs-privilege` (sudo refused), `unreachable` (ssh exit 255 or timeout), `missing` (status only: the fixed probe of hostname, `/etc/os-release`, uptime and `rootfiles --version` shows no binary), `error`. Check/doctor exit 2 without valid JSON stdout is `error`, using the remote diagnostic rather than treating usage failures as report findings. Valid JSON retains the existing syntax-only acceptance; this rule adds no schema requirement. Remote status JSON with `config_error` or `module_check_error` is `error` (`inspectStatusHealth`). Text uses the shared wrapped result table above; JSON embeds the remote JSON verbatim. Exit 0 when every host is `ok`, 2 for other host results; controller errors follow the parsing/other error codes above. `--view gpu|users` (`writeFleetView`) adds a section parsed from that same remote `status -o json` in `Result.Remote`, so no remote command line changes and the sudoers bytes stay as they are; a host that did not report the section renders `-`, JSON adds the section beside `hosts` under the view's own key, and without `--view` the text and JSON are byte-identical to the report without it.
- **`fleet apply`**: requires a site config per host. Runs remote `status` first and proceeds only on `ok`, `drift`, an unverified fingerprint or an ambiguous home base, with remote OS evidence. It then validates module capabilities locally against the remote `SystemInfo` (`module.NewRegistry().Resolve` + `config.ValidateCapabilities`), so an unsupported module on a Rocky host fails before any write. `--dry-run` pipes the config to `rootfiles apply --yes --dry-run --config -`. A real run stores the config at `/etc/rootfiles/fleet/<host>-<sha256>.yaml` (root, 0600, immutable: an existing file with other content is refused), verifies the checksum on the host, restores `umask 022` (#74) and execs `rootfiles apply --yes --config <path>` (`persistAndApplyScript`). Later `check`/`status`/`doctor` then use the applied config.
- **`fleet update --version vX.Y.Z`**: runs the remote `rootfiles update --version`, then a read-only `check` with the new binary (`postUpdateCheck`). Drift backed by valid JSON becomes `apply-pending` with the unsatisfied module names; nothing is applied. An exit-2 post-check without valid JSON remains `error` with its diagnostic and stops the serial rollout, even though the binary update succeeded. `apply-pending` does not stop the rollout, and the run ends with a hint to run `fleet check` and `fleet apply` for those hosts (#70).
- **`fleet bootstrap --version vX.Y.Z`**: skips hosts where status proves rootfiles is installed; installs only on `missing` (or unverified with OS evidence) hosts by downloading the pinned linux amd64/arm64 release and `checksums.txt` from GitHub, verifying with `sha256sum -c`, and installing `/usr/local/bin/rootfiles` root 0755.
- **`fleet schedule enable|disable`**: runs the remote `rootfiles schedule <action>`.
- **`--skip-unreachable`** (apply, update, bootstrap, schedule; #70): a host whose ssh connection fails (exit 255, not a timeout) becomes `skipped-unreachable` and the rollout continues; any other failure still stops it. The run prints a rerun command for the skipped hosts (`fleetRerunCommand`) and logs the op with the flag.
- **`fleet targets [--push <hub> --yes]`**: renders Prometheus `file_sd` JSON from the whole inventory (`RenderTargets`): one entry per host with `address` and an enabled exporter in its site config, port from `NodePort()`/`DCGMPort()`, labels `host`, `exporter` (`node`|`dcgm`) and `group_<name>=true`. `--push` requires `--yes`, a hub host whose site config enables `modules.monitoring.hub`, and a `targets_file` that passes `config.ValidateMonitoringDiscoveryPath`. The push script (`fleetTargetsPushScript`) refuses symlinks and untrusted parents, creates missing parents root 0755, and replaces the file atomically (temp file, `mv`). Prometheus re-reads `file_sd` itself; the push restarts nothing. `--dry-run` reports the path only.
- **Every mutating run and push** appends one JSON line to the run log (time, operator, command, per-host results). Remote failure reasons prefer the last `rootfiles: ` diagnostic, then the last legacy `Error:` line, then the last nonempty stderr line excluding Unicode/ASCII next-step prefixes. The existing combined-output/default fallbacks remain, and reasons are capped at 240 characters (`shortReason`).
- **`fleet log [--host] [--op] [--since] [--limit] [-o text|json] [--json]`** (`ReadFleetHistory`, `newFleetLogCmd`): reads that log back newest first, one row per run and host with time, operation, host, state, exit code and reason. `--host` keeps runs that touched the host and returns the record whole, `--op` matches the recorded command's first word (so `targets` also matches `targets --push <hub>`), `--since` accepts a duration, whole days, a UTC date or an RFC 3339 timestamp, and `--limit` caps runs rather than rows. JSON reprints the stored line byte for byte (`HistoryEntry.Line`), never a re-encoding, so an unknown field survives. A missing log is an empty result with exit 0; a corrupt line is named with its 1-based line number on stderr and skipped so one bad write cannot hide the rest. It reads the controller's own file: no inventory, no SSH, no host lock, no root.
- **`fleet shutdown schedule|now|cancel|status`** (`internal/fleet/shutdown.go`, `internal/cli/fleet_shutdown.go`): one absolute UTC instant is computed once and sent to every host, so simultaneity never depends on SSH ordering; scheduling stays serial and stops at the first failure. Before anything is written, every selected host is pre-flighted (`shutdownPreflight`): `date -u +%s` over plain ssh (never sudo, so the read-only rule stays untouched) must be within `MaxClockSkew` (30s) of the controller, the host's `rootfiles shutdown status -o json` must answer (proving the binary has the command) and must not report `scheduled_shutdown_error` (a state file the host cannot read is a timer that may still be armed, so it stops the run with that host's cancel command), and it must report no schedule unless `--replace` is given. One failing host makes every other host `skipped` ("not attempted") with no write. A failure during scheduling treats every host the run touched as uncertain and cancels it, including the failing one, whose schedule can have enabled the poweroff timer before a later notice timer failed: the others report `cancelled`, and any cancel that fails reports `cancel-failed` with the exact `fleet shutdown cancel --host ... --yes` rerun command, `--yes` included because a real cancel is confirmed by it. A host that reports `shutdown.ErrUntouched` failed before writing anything, so it is reported `error` with "nothing was cancelled" instead: cancelling it would remove a schedule the operator never replaced. `cancel` is the one mutating fleet command that continues past failures and exits 2 if any host failed. `now` is `schedule` with `At = controller now + --in + ShutdownMargin` (default 2m, minimum 1m): the margin is `MaxClockSkew` plus 5s, because the instant loses its sub-second part and the host validates the lead again against a clock that may be the full skew ahead, so `--in 1m` must not arrive there as 59 seconds. Both ends of that window are enforced rather than assumed: `--in` above `MaxLead - ShutdownMargin` is refused by the controller, since adding the margin would hand the host a lead past its own 30-day maximum, and `ShutdownSchedule` refuses the whole run before any host is contacted when the instant is closer than `MinLead + MaxClockSkew`, because the preflight and the delivery take time a bare minimum does not account for. The controller's own host is refused without `--include-self`: `controllerHostsIn` refuses a host whose inventory name, ssh destination or `address` is this machine's hostname or one of its non-loopback interface addresses, on any port, and one whose destination the local `ssh -G` resolves to a loopback name or address on the controller's own ssh port (`controllerSSHPort`, 22). A loopback address is an interface address of the controller too, but it proves nothing on its own: it is classified with the loopback names, because on any other port it reaches a different machine. A loopback destination on any other port is a forwarded host rather than this machine - the distinction ssh itself draws when it keys known_hosts by `[127.0.0.1]:2222` rather than by `127.0.0.1` - so a fleet reached through local port forwards stays schedulable, which is how `tests/scenarios/fleet.sh` reaches both of its containers; an inventory that reaches the controller's own sshd on a non-standard port must name it by hostname or address, because no alias read can tell those apart. A resolved destination is also looked up (`resolveHost`): a DNS name or CNAME that resolves to one of this machine's addresses is this machine. The check fails closed - a hostname or interface list that cannot be read, or an `ssh -G` that cannot answer, refuses the run instead of passing it - while a name that resolves nowhere is not this machine, and the preflight would fail there before any timer was set. So an alias or a loopback address cannot carry the rollout onto the controller. `status` reuses the read-only pool and the `SHUTDOWN` column (`writeFleetStatusResults`), which the table drops when no host has a schedule, so a fleet without one renders exactly the previous text and a host whose state file cannot be read shows `unknown`; the JSON report is untouched because each schedule already lives in that host's own payload. Every run appends to the run log with the instant, the action and the message (`shutdownRunLogCommand`). Host-side units, the login block and the state file are [shutdown](shutdown.md).
- **Read-only sudoers** (`users.fleet_sudo_users`, applied by the `users` module, see [users](users.md)): writes `/etc/sudoers.d/rootfiles-fleet` with one `Cmnd_Alias ROOTFILES_FLEET_READONLY` granted `NOPASSWD` to the sorted user list. Check and Apply refuse when `/usr/local/bin/rootfiles` or any ancestor is a symlink, not root-owned, or group/world-writable (`validateFleetSudoBinary`). Users must exist (Check also accepts users declared in `users.accounts`). The file goes through `installSudoersFile` (temp file 0440, `visudo -cf`, rename), and Apply verifies the effect with `sudo -l -U <user>`. An empty list removes the drop-in. Config validation of the list lives in `internal/config/monitoring_validate.go` (users module must be enabled; valid, unique names).

## Distro support

- Controller: Linux and macOS (darwin/arm64 is built in CI and released by `.goreleaser.yaml`). It needs only OpenSSH locally.
- Remote scripts assume GNU coreutils (`stat -c`, `sha256sum`, `install`, `mktemp`) plus `curl` and `tar` for bootstrap; bootstrap supports linux amd64 and arm64.
- Rocky hosts: reporting works; `fleet apply` refuses modules unsupported on the remote distro before sending anything (capability check above, see [distro-rocky](distro-rocky.md)). The sudoers drop-in works on Ubuntu and Rocky (`users` is supported on both).

## Safety

- Generated-file comparisons preserve legacy headers using the [shared managed-header rule](exec-packages.md#contracts-and-invariants); changing the marker alone never rewrites a converged file or reloads its service.

- Host key verification is inherited from OpenSSH; there is no flag to disable it.
- The only passwordless privilege the feature adds is the three-command read-only rule. `installSudoersFile` is shared with the tenant operator rule (`internal/module/tenant.go`); keep its temp-file, `visudo -cf` and rename order.
- Secrets reach hosts only as files on the host (`tunnel_token_file`, `alert_receiver_file`); inline secrets in site configs are refused at inventory load.
- Rollout practice (from the 2026-10-03 rollout): publish and download a checksummed release; keep prior binaries, site configs, state and service configs for recovery; preserve GPU drivers, running containers and existing web ports; report unreachable hosts and unsupported modules explicitly. An unreachable host is never a successful deployment.
