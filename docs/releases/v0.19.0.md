The `dgx` profile no longer carries a tunnel VLAN address, `full` no longer switches on a network module that did nothing, and `config validate` rejects an enabled private network with no address.

### Improved
- The `dgx` profile no longer sets `modules.cloudflared.private_network`: the tunnel VLAN address belongs to the site that owns it. Its `network.allowed_ports` now lists only 80 and 443 (the SSH port is always admitted), and the copy of `ssh.disable_root_login` that `minimal` already sets is gone. (#101)
- The `gpu-server` profile no longer asks for a tunnel VLAN with an empty address, which configured nothing, or for the SSH port in `allowed_ports`. (#101)
- The `full` profile keeps only what `minimal` does not set: Docker and storage. Its `network` block never enabled UFW, so it changed nothing on a host; it is gone rather than turned into a firewall change for hosts already using the profile. (#101)
- `rootfiles config validate` now rejects `modules.cloudflared.private_network.enabled: true` without an address and names the key, where apply used to finish without configuring anything. (#101)

### Action needed
- A DGX host that uses the tunnel's private VLAN must set the address in a site config that extends `dgx` (under `modules.cloudflared.private_network`: `enabled`, `interface` and `address`), then run `sudo rootfiles apply` or `rootfiles fleet apply`; `docs/fleet.example.yaml` shows the file. Without it the profile stops configuring the VLAN but does not remove an interface an earlier apply created; `rootfiles tunnel uninstall` removes it. (#101)
- A site config that sets `private_network.enabled: true` without an address now fails `rootfiles config validate` and the apply that follows it: add the address or set `enabled: false`. (#101)
